- `chip-router`: `PublishBatch` returns one `PublishResult` per event (previously an empty response, which made node durable emitters retransmit the whole stream), aggregating subscribers' per-event outcomes independent of completion order and honoring `transaction_enabled`; an empty batch is a no-op success
- `chip-router`: a subscriber response with a result count different from the batch size is ignored as a failed forward; an empty response still counts as a detail-less success. When no subscriber is usable, the `Internal` error names each failing subscriber (name, endpoint), what it did (RPC error, or `returned N results for M events`) and what a correct response is, instead of a bare count
- `chip-router`: `Publish` (single event) is all-or-nothing like the chip-ingress write-service: it fails unless a subscriber accepted the event and returns exactly one `PublishResult`
- `chip-router`: failures return `codes.Internal` (the write-service's failure code), including when no subscribers are registered or none accepted, instead of acking undelivered events; the messages say how to fix the cause (register a subscriber via `POST /subscribers`; which events a `transaction_enabled` batch rejected and that dropping `transaction_enabled` delivers the rest)
- `chip-router`: implement `Ping` like the write-service
